# API Contract

The agreement between the React frontend in `frontend/` and the Spring Boot backend. Both sides implement this document; neither changes it alone.

Base URL comes from `VITE_API_URL` on the frontend, defaulting to `/api`.

## Principles

**The client sends identifiers, the server owns money.** A request carries `productId`, `quantity` and the ids of the chosen options. It never sends a price. The server looks every price up in its own tables, computes the totals, and returns them. Prices in the frontend's menu data exist only to render the screen; they are never trusted as input.

**Money travels as a string.** `"15.50"`, not `15.5`. A JSON number is parsed into a JavaScript double, which is where `3.3 * 3` becomes `9.899999999999999`. A string carries the exact `DECIMAL(10,2)` value from the database to the screen untouched. Every monetary field in this document is a string with exactly two decimal places, and every response that contains one also carries `currency`.

**Currency is AUD.** Displayed with a plain dollar sign — `$8.50`, never `A$8.50` or `AUD 8.50`. The frontend enforces this in `lib/formatPrice.js`.

## GET /api/menu

Returns the full menu in one call. It is cached client-side for five minutes.

```json
{
  "currency": "AUD",
  "categories": [
    { "id": "food", "name": "Food", "sortOrder": 1 },
    { "id": "coffee", "name": "Coffee", "sortOrder": 2 }
  ],
  "products": [
    {
      "id": 201,
      "categoryId": "coffee",
      "station": "FRONT_OF_HOUSE",
      "name": "Signature Latte",
      "description": "Smooth espresso with creamy milk",
      "price": "6.50",
      "image": "https://images.unsplash.com/photo-...",
      "tags": ["Popular"],
      "available": true,
      "optionGroups": [
        {
          "id": "size",
          "name": "Size",
          "type": "single",
          "required": true,
          "options": [
            { "id": "small", "name": "Small", "price": "0.00" },
            { "id": "large", "name": "Large", "price": "1.00" }
          ]
        },
        {
          "id": "sugar",
          "name": "Sugar",
          "type": "counter",
          "required": false,
          "unit": "tsp",
          "defaultValue": 0,
          "min": 0,
          "max": 10
        }
      ],
      "addonGroups": [
        {
          "id": "syrup",
          "name": "Syrup",
          "type": "multi",
          "options": [
            { "id": "vanilla", "name": "Vanilla Syrup", "price": "0.50" }
          ]
        }
      ]
    }
  ]
}
```

Notes:

- `categoryId` replaces matching on a display string, so renaming a category cannot silently hide its products.
- `station` is `KITCHEN` or `FRONT_OF_HOUSE`. It drives docket routing and belongs to the product, not the category, because categories get reorganised and stations do not.
- `available: false` keeps a sold-out product in the response so the UI can grey it out rather than have it vanish mid-session.
- `optionGroups` are single-choice or counter and affect the base configuration. `addonGroups` are multi-choice extras. A `counter` group carries `unit`, `defaultValue`, `min` and `max`; the frontend treats a missing `max` as unbounded and a missing `min` as zero, but the server should always send both.

## POST /api/orders

### Request

```json
{
  "idempotencyKey": "9f1c2e7a-4b3d-4f8a-9c21-0d5e6f7a8b90",
  "tableNumber": 7,
  "customer": {
    "name": "Vinh",
    "phone": "0400123456"
  },
  "notes": "No cutlery please",
  "items": [
    {
      "productId": 201,
      "quantity": 2,
      "options": [
        { "groupId": "size", "optionId": "large" },
        { "groupId": "milk", "optionId": "oat" }
      ],
      "addons": [
        { "groupId": "syrup", "optionId": "vanilla" }
      ],
      "counters": [
        { "groupId": "sugar", "value": 2 }
      ]
    }
  ]
}
```

| Field | Required | Notes |
|---|---|---|
| `idempotencyKey` | yes | UUID v4 generated by the client, once per order attempt |
| `tableNumber` | yes | positive integer |
| `customer.name` | yes | non-blank after trimming |
| `customer.phone` | no | free text; not validated as a phone number |
| `notes` | no | order-level note |
| `items` | yes | at least one entry |
| `items[].quantity` | yes | positive integer |
| `options` / `addons` / `counters` | no | omit or send an empty array when unused |

`options` and `addons` are arrays of objects rather than a map keyed by group id. A map with dynamic keys is awkward to validate and to map onto entities in Java; an array deserialises straight into a `List` of a two-field DTO and joins cleanly onto an `order_item_option` table.

`counters` is separate from `options` because it carries a quantity rather than a choice. Two teaspoons of sugar is a different kind of thing from a Large size.

### Response — 201 Created

```json
{
  "orderId": "01J9XQ2M4S7B8K3N5P6R7T8V9W",
  "orderNumber": "A-042",
  "status": "RECEIVED",
  "placedAt": "2026-09-02T10:14:32Z",
  "tableNumber": 7,
  "currency": "AUD",
  "total": "15.50",
  "items": [
    {
      "productId": 201,
      "name": "Signature Latte",
      "quantity": 2,
      "unitPrice": "7.75",
      "lineTotal": "15.50",
      "station": "FRONT_OF_HOUSE",
      "modifiers": ["Large", "Oat Milk", "2 tsp Sugar"]
    }
  ]
}
```

- `orderId` is the internal identifier. `orderNumber` is the short human-readable code shown to the customer and printed on the docket.
- `status` is one of `RECEIVED`, `IN_PROGRESS`, `READY`, `COMPLETED`, `CANCELLED`.
- `unitPrice` is the price of one unit with its options and addons included; `lineTotal` is `unitPrice × quantity`. Both are computed server-side.
- `modifiers` is a pre-rendered list of labels so the frontend and the docket printer do not each have to reassemble them from ids.

### Idempotency

`idempotencyKey` is stored with a unique constraint. A repeat request carrying a key that already exists must **return the existing order with 200 OK** rather than create a second one or fail.

This is what actually prevents two dockets reaching the kitchen. The frontend's disabled button only stops a second click; it cannot stop a request that was retried after a timeout, or a customer who pulled down to refresh at the wrong moment.

The key is generated once when the checkout screen mounts, and regenerated only after an order succeeds.

## Errors

Errors follow RFC 7807, which Spring Boot 3 supports natively through `ProblemDetail`, plus one added `code` field for the frontend to branch on.

```json
{
  "type": "https://api.mycoffeehouse.au/errors/product-unavailable",
  "title": "Product unavailable",
  "status": 422,
  "detail": "Signature Latte is no longer available",
  "instance": "/api/orders",
  "code": "PRODUCT_UNAVAILABLE"
}
```

The human-readable message is in `detail`. The frontend reads `detail` first and falls back to `title`.

| Status | `code` | When |
|---|---|---|
| 400 | `VALIDATION_FAILED` | malformed body, missing required field |
| 404 | `PRODUCT_NOT_FOUND` | a `productId` does not exist |
| 422 | `PRODUCT_UNAVAILABLE` | product exists but `available` is false |
| 422 | `INVALID_MODIFIER` | an option id does not belong to that product's group |
| 422 | `REQUIRED_OPTION_MISSING` | a required group has no selection |
| 500 | `INTERNAL_ERROR` | anything unhandled |

## Notes for the Spring Boot side

- Serialise money with `BigDecimal` mapped to `DECIMAL(10,2)`, and configure Jackson to write it as a string — either `WRITE_BIGDECIMAL_AS_PLAIN` together with a `toPlainString` serialiser, or `@JsonFormat(shape = STRING)` on the field. Never let a monetary field reach JSON as a number.
- Recompute every price from the database on every order. Treat the request body as untrusted input.
- Validate that each `optionId` actually belongs to the `groupId` sent, and that the group belongs to that product. Otherwise a caller can attach a cheap product's discount option to an expensive one.
- Enforce required option groups server-side as well. The frontend disables its button, but that is a convenience, not a control.
